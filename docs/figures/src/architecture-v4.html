Data formats
What actually travels on each lettered arrow (field names as in the code)

AHome sensors → Sensor reader

JSON snapshot every 1 s, appended to readings.jsonl; latest.csv = ts, source, metric, value
{"ts":"2026-11-26T18:05:01","tariff":"peak",
 "rooms":{"Kitchen":{"temp":31.5,"humidity":48.0}},
 "appliances":{"washer":{"cycle":"done",
   "door_closed":true,"drum_humidity":90.0}},
 "occupancy":{"user_home":false},
 "total_load_w":3120}

BCalendar → Sensor reader

calendar.json: JSON array, ISO 8601 times; read at start and on reload
[{"title":"Dinner bake",
  "start":"2026-11-26T18:30",
  "end":"2026-11-26T19:30"}]

CTariff & CO₂ data → Region presets

Copied by hand from the publisher into a Python dict in regions.py, with the source named
"KR": {"currency":"KRW","price":214.6,
  "peak":220.5,"offpeak":138.7,
  "peak_hours":"16-22",
  "co2_kg_per_kwh":0.4173,
  "tariff_source":"KEPCO","co2_source":"MCEE 2023"}

DUsers ↔ REST API

HTTPS + JSON. Screen polls every 4 s; alerts pushed as Server-Sent Events
POST /api/chat  {"text":"turn off the bedroom AC"}
GET  /api/snapshot           (every 4 s)
POST /api/approvals/<id>/confirm | decline
GET  /api/events   (SSE)
data: {"kind":"approval","title":"Your home
       needs an answer","body":"..."}

EServer ↔ LLM API

OpenAI-compatible POST /chat/completions; the reply is a tool call that code validates before use
{"model":"glm-4-flash","temperature":0,
 "messages":[{"role":"system","content":"..."},
             {"role":"user","content":"..."}],
 "tools":[...],"tool_choice":"auto"}

FDevice adapter ↔ Appliances

Inside: one action format for every device. ThinQ turns it into LG's JSON payload
apply("washer",
      [{"action":"ventilate","value":true}])
→ {"ok":true,"applied":[...],"error":null}

ThinQ: {"operation":{"airConOperation":
         {"power":"POWER_OFF"}}}

GAudit gate → SQLite audit_log

Two rows per action: action.intent before, action.executed / failed after. Rows cannot be edited or deleted
ts, event_type="action.intent", risk_kind="mold",
risk_score=78, action_kind, tier="tier1",
approval_id, execution_status="pending",
decision_source, channel, device_id, detail

·Inside: budget verdict

budget.can_start() on every path; a DELAY becomes a scheduled job, re-checked when due
{"decision":"DELAY","limit":"max_kw",
 "device":"Balcony Dryer","load_kw":1.8,
 "after_kw":3.2,"max_kw":3.0,"band":"peak",
 "scheduled_at":"2026-11-27T22:00",
 "remaining_kwh":96.4}
main data flow safety path (policy → approval → budget gate → audit → device) running in the demo optional / code-ready
Demo note: the house is simulated — sensor values and appliance state come from a simulator that plays the part of the external sources; the system reads them only through the Input layer and the Device adapter, so a real ESP32 or LG ThinQ swaps in without changing layers ②–⑤.
